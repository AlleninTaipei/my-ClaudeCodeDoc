Monitoring Claude Code

Track usage, costs, and tool activity by exporting telemetry through OpenTelemetry — metrics as time series, events via logs, and optionally distributed traces, all sent to backends you configure and own.

Quick start

Configure OpenTelemetry using environment variables, one step at a time:

Enable telemetry

export CLAUDE_CODE_ENABLE_TELEMETRY=1

Choose exporters (both optional — configure only what you need)

export OTEL_METRICS_EXPORTER=otlp       # Options: otlp, prometheus, console, none
export OTEL_LOGS_EXPORTER=otlp          # Options: otlp, console, none

Configure OTLP endpoint (for OTLP exporter)

export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317

Set authentication (if required)

export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer your-token"

For debugging: reduce export intervals

export OTEL_METRIC_EXPORT_INTERVAL=10000  # 10 seconds (default: 60000ms)
export OTEL_LOGS_EXPORT_INTERVAL=5000     # 5 seconds (default: 5000ms)
NOTE

The default export intervals are 60 seconds for metrics and 5 seconds for logs. Use shorter intervals for debugging, and remember to reset them for production use.

Run Claude Code

claude

For full configuration options, see the OpenTelemetry specification's exporter configuration reference.

Step 1 of 6

Administrator configuration

Administrators can configure OpenTelemetry settings for all users through the managed settings file, for centralized control across an organization. Example managed settings configuration:

{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.example.com:4317",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer example-token"
  }
}
NOTE

Managed settings can be distributed via MDM or other device management solutions. Environment variables defined there have high precedence and can't be overridden by users.

Claude Code doesn't pass OTEL_* environment variables to subprocesses it spawns, including the Bash tool, hooks, MCP servers, and language servers. An instrumented application run through the Bash tool doesn't inherit Claude Code's exporter endpoint or headers — set those variables directly in the command if that application needs to export its own telemetry.

Distributed tracing exports spans that link each user prompt to the API requests and tool executions it triggers, so you can view a full request as a single trace. Tracing is off by default. REDACTION

Spans redact user prompt text, tool input details, and tool content by default. Set OTEL_LOG_USER_PROMPTS=1, OTEL_LOG_TOOL_DETAILS=1, and OTEL_LOG_TOOL_CONTENT=1 to include them.

When tracing is active, Bash and PowerShell subprocesses automatically inherit a TRACEPARENT environment variable with the W3C trace context of the active tool span, letting any subprocess that reads it parent its own spans under the same trace. When connected directly to the Anthropic API, each model request carries a W3C traceparent header and the API's traceresponse is recorded as a span link; the header is not sent to third-party providers. By default it's sent only when ANTHROPIC_BASE_URL is unset or points at the Anthropic API — set CLAUDE_CODE_PROPAGATE_TRACEPARENT=1 to propagate through a custom proxy. In Agent SDK and non-interactive -p sessions, Claude Code also reads inbound TRACEPARENT/TRACESTATE so its spans nest under the caller's distributed trace; interactive sessions ignore inbound values to avoid inheriting ambient CI/container context.

Span hierarchy

Each user prompt starts a claude_code.interaction root span. API calls, tool calls, and hook executions are its children. Tool spans have two children: time waiting on a permission decision, and the execution itself. When the Agent tool spawns a subagent, its spans nest under the parent's claude_code.tool span.

claude_code.interaction
├── claude_code.llm_request
├── claude_code.hook                    (requires detailed beta tracing)
└── claude_code.tool
    ├── claude_code.tool.blocked_on_user
    ├── claude_code.tool.execution
    └── (Agent tool) subagent claude_code.llm_request / claude_code.tool spans

In Agent SDK and claude -p sessions, claude_code.interaction becomes a child of the caller's span when TRACEPARENT is set.

For enterprise environments needing dynamic authentication, configure a script to generate headers dynamically. Dynamic headers apply only to http/protobuf and http/json; the grpc exporter uses only the static OTEL_EXPORTER_OTLP_HEADERS value.

Settings configuration

// .claude/settings.json
{
  "otelHeadersHelper": "/bin/generate_opentelemetry_headers.sh"
}

The value can be a path to an executable, including one with spaces, or a shell command line with arguments. On Windows the value always runs through the shell, so quote a path containing spaces.

Script requirements

The script must output valid JSON with string key-value pairs representing HTTP headers:

#!/bin/bash
# Example: Multiple headers
echo "{\"Authorization\": \"Bearer $(get-token.sh)\", \"X-API-Key\": \"$(get-api-key.sh)\"}"

If the helper fails or prints non-conforming output, Claude Code reports the error in /status, the debug log (--debug or /debug), or stderr in non-interactive -p sessions.

Refresh behavior

The headers helper script runs at startup and periodically thereafter, every 29 minutes by default. Customize with CLAUDE_CODE_OTEL_HEADERS_HELPER_DEBOUNCE_MS.

Organizations with multiple teams can add custom attributes to distinguish groups using OTEL_RESOURCE_ATTRIBUTES:

export OTEL_RESOURCE_ATTRIBUTES="department=engineering,team.id=platform,cost_center=eng-123"

These attributes are included in all metrics and events, letting you filter by team, track cost per center, build team dashboards, and set team-scoped alerts. They're attached to every metric datapoint and event record, plus sent in the OTLP resource block, so most metrics backends can group and filter by them directly. Custom keys never override the standard attributes such as user.id or session.id — Claude Code keeps the built-in value on collision.

Each custom key becomes a label on every metric series, so high-cardinality values increase storage cost. Set OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES=false to send them in the resource block only.

WARNING

No spaces allowed in values — user.organizationName=My Company is invalid. Format: comma-separated key=value pairs. Allowed characters: US-ASCII excluding control characters, whitespace, quotes, commas, semicolons, backslashes. Special characters outside that range must be percent-encoded. Quoting a value doesn't escape spaces — it produces the literal quoted string.

# Use underscores or camelCase instead of spaces
export OTEL_RESOURCE_ATTRIBUTES="org.name=Johns_Organization"
export OTEL_RESOURCE_ATTRIBUTES="org.name=JohnsOrganization"

# Or percent-encode
export OTEL_RESOURCE_ATTRIBUTES="org.name=John%27s%20Organization"

Interpret metrics and events data

Usage monitoring

claude_code.token.usage — break down by type, user, team, model, skill, plugin, or agent.

claude_code.session.count — track adoption and engagement over time.

claude_code.lines_of_code.count — measure productivity, broken down by model.

claude_code.commit.count & pull_request.count — understand impact on development workflows.

Cost monitoring

claude_code.cost.usage helps track spend trends across teams, identify high-usage sessions, and attribute spend to skills, plugins, or subagent types.

NOTE

Cost metrics are approximations. For official billing, refer to your API provider.

Alerting and segmentation

Common alerts: cost spikes, unusual token consumption, high session volume from specific users. All metrics can be segmented by the standard attributes. The model attribute is available on token, cost, and (from v2.1.172) lines_of_code metrics. Per-model commit breakdowns can only be approximated by joining against token/cost metrics on session.id, filtered to query_source: "main" so subagent requests don't misattribute commits.

Detect retry exhaustion

Claude Code retries internally and emits a single api_error event only after giving up — intermediate attempts aren't logged separately. The attempt attribute records the total. CLAUDE_CODE_MAX_RETRIES defaults to 10, capped at 15 (removed by CLAUDE_CODE_RETRY_WATCHDOG as of v2.1.199); exhaustion on a transient error means attempt equals one more than the effective limit. A lower value indicates a non-retryable error such as a 400. To distinguish recovery from stalling, group by session.id and check for a later api_request event after the error.

Event analysis

Tool usage patterns: analyze tool_result events for most-used tools, success rates, average execution times, and error patterns by tool type. Performance monitoring: track API request durations and tool execution times to find bottlenecks.

Audit security events

OpenTelemetry events are the audit data source for Claude Code activity. Every event carries identity attributes tying tool calls, MCP activity, and permission decisions back to the user who triggered them. The OTLP logs exporter can deliver these to any SIEM with an OTLP receiver, or to a Collector that forwards to your SIEM.

The standard attributes include the authenticated user's identity: user.email, user.account_uuid, user.account_id, organization.id when signed in, plus user.id and session.id. Claude Code doesn't act under a separate service account — every event is attributed to the developer's own account (or IdP identity on a gateway session). With a direct API key, Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry, there's no Claude account in the session, so attach identity yourself:

export OTEL_RESOURCE_ATTRIBUTES="enduser.id=jdoe@example.com,enduser.directory_id=S-1-5-21-..."

Audit MCP activity

Enable the logs exporter and set OTEL_LOG_TOOL_DETAILS=1 to capture full MCP call detail:

Backend considerations

For metrics
  • Time series DBs (Prometheus): rate calculations, aggregated metrics
  • Columnar stores (ClickHouse): complex queries, unique user analysis
  • Full observability platforms (Honeycomb, Datadog, Grafana Cloud): advanced querying, visualization, alerting
For events/logs
  • Log aggregation (Elasticsearch, Loki): full-text search, log analysis
  • Columnar stores (ClickHouse): structured event analysis
  • Full observability platforms: correlation between metrics and events
For traces
  • Distributed tracing (Jaeger, Zipkin, Grafana Tempo): span visualization, request waterfalls, latency analysis
  • Full observability platforms: trace search and correlation with metrics and logs

For organizations requiring DAU/WAU/MAU metrics, consider backends that support efficient unique value queries.

Security and privacy

Opt-in exportOpenTelemetry export requires explicit configuration. Anthropic's separate operational telemetry is a different system — see Data usage for how to disable it.
No file contentsRaw file contents and code snippets are not included in metrics or events. Trace spans are a separate path, gated by OTEL_LOG_TOOL_CONTENT.
user.emailIncluded in attributes when authenticated via OAuth. Filter or redact at your telemetry backend if this is a concern.
Prompt contentNot collected by default — only length. Set OTEL_LOG_USER_PROMPTS=1 to include it.
Response contentNot collected by default — only length. Set OTEL_LOG_ASSISTANT_RESPONSES=1; falls back to OTEL_LOG_USER_PROMPTS when unset.
Tool argumentsNot logged by default. OTEL_LOG_TOOL_DETAILS=1 adds tool_parameters and tool_input to events, and file_path-style attributes to spans, truncated to ~4K characters.
Tool contentNot logged in trace spans by default. OTEL_LOG_TOOL_CONTENT=1 adds full input/output content to span events, truncated at 60 KB per span.
Raw API bodiesNot logged by default. OTEL_LOG_RAW_API_BODIES includes the full conversation history — implies consent to everything the other OTEL_LOG_* flags would reveal. Extended-thinking content is always redacted regardless of other settings.

Every OTel signal Claude Code exports goes only to the endpoint you configure — never to Anthropic.
