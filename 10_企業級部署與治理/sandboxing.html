Configure the Sandboxed Bash Tool

了解 Claude Code 內建的 sandboxed Bash tool 如何提供檔案系統與網路隔離, 讓 agent 能更安全, 更自主地執行。

Get started 開始使用

1 · 執行 /sandbox
2 · 選擇模式
3 · 執行 Bash 指令

啟動 Claude Code session 後執行 /sandbox, 會開啟含三個分頁的沙盒面板: Mode (核准方式), Overrides (是否允許失敗時退回非沙盒執行), Config (檢視已解析的沙盒設定)。若只看到 Dependencies 分頁, 表示缺少必要套件。

在 Mode 分頁選擇 auto-allow 或一般權限。Auto-allow 會直接執行沙盒化指令不詢問, 一般權限則維持提示。

請 Claude 執行指令, 例如 build 或測試。預設沙盒化指令只能寫入工作目錄與 session 暫存目錄, 第一次需要新網域時會提示核准。

Step 1 of 3

Set up Linux and WSL2

Linux 與 WSL2 上, 沙盒需要兩個套件: bubblewrap (檔案系統隔離) 與 socat (網路流量轉送)。

選擇發行版:
Ubuntu/Debian
Fedora
sudo apt-get install bubblewrap socat
sudo dnf install bubblewrap socat
NOTE

Ubuntu 24.04 以上版本, 預設 AppArmor 政策會阻止 bubblewrap 建立所需的 user namespace, 需另外新增 AppArmor profile 授權。WSL1 不支援沙盒, 需升級到 WSL2。

Sandbox modes

Auto-allow mode

Bash 指令會嘗試在沙盒中執行並自動核准, 無法沙盒化的指令 (如需要存取未允許主機) 則退回一般權限流程。

Regular permissions mode

所有 Bash 指令都走一般權限流程, 即使已沙盒化。控制力更高, 但需要更多核准。

即使在 auto-allow 模式下, 明確的 deny 規則, 針對 / 或家目錄的 rm, 以及內容範圍的 ask 規則 (如 Bash(git push *)) 仍然適用。

Configure sandboxing 設定沙盒

透過 settings.json 自訂沙盒行為。預設沙盒化指令只能寫入目前工作目錄與 session 暫存目錄, 可用 sandbox.filesystem.allowWrite 授權額外路徑:

{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "allowWrite": ["~/.kube", "/tmp/build"]
    }
  }
}

路徑前綴的解析規則:

/ (絕對路徑)從檔案系統根目錄, 例如 /tmp/build 維持 /tmp/build
~/ (家目錄相對)相對於家目錄, 例如 ~/.kube 變成 $HOME/.kube
./ 或無前綴相對於專案根目錄 (專案設定) 或 ~/.claude (使用者設定)

Protect credentials

sandbox.credentials 設定可宣告沙盒化指令不得存取的憑證檔案與環境變數 (需 Claude Code v2.1.187 以上):

{
  "sandbox": {
    "enabled": true,
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "NPM_TOKEN", "mode": "deny" }
      ]
    }
  }
}
NOTE

沒有內建的憑證封鎖清單, 只有你列出的檔案與變數才會被限制。此設定只影響沙盒化的 Bash 指令。

How sandboxing works 運作原理

選擇面向:
檔案系統隔離
網路隔離
OS 層級強制
預設寫入行為讀寫目前工作目錄及其子目錄, 加上 $TMPDIR 指向的 session 暫存目錄
預設讀取行為可讀取整台電腦, 除特定拒絕目錄外; 仍可讀取 ~/.aws/credentials 等憑證檔案, 需另用 sandbox.credentials 封鎖
封鎖存取無法修改工作目錄與暫存目錄以外的檔案, 包含 ~/.bashrc 與 /bin/ 下的系統執行檔
網域限制預設沒有任何網域被允許, 第一次需要新網域時會提示核准, 之後同一台主機不再詢問 (v2.1.191 起)
Managed lockdown設定 allowManagedDomainsOnly 後, 未核准網域會被自動封鎖而非提示
自訂 proxy進階使用者可自行實作對外流量的規則
macOS使用 Seatbelt 強制執行沙盒
Linux使用 bubblewrap 進行隔離
WSL2與 Linux 相同使用 bubblewrap; WSL1 不支援

How sandboxing relates to permissions and permission modes

沙盒, 權限規則與權限模式是互補的三層機制。

Permission rules

控制 Claude Code 能使用哪些工具, 在任何工具執行前先評估, 適用於 Bash, Read, Edit, WebFetch, MCP 等全部工具。

Sandboxing

提供 OS 層級的強制執行, 限制 Bash 指令與其子行程在檔案系統與網路層面能存取的範圍, 只適用於 Bash。

兩者的強制方式也不同: 權限決策在指令執行前依指令字串評估, 而作業系統則在執行中的行程上強制執行沙盒邊界, 因此不論模型選擇執行什麼, 邊界都持續有效。

Permission modes

/sandbox控制 Bash 指令執行後能存取什麼; 由沙盒邊界本身取代提示 (auto-allow 模式下)
Auto mode控制每個工具呼叫是否執行; 由分類器審查動作取代提示
--dangerously-skip-permissions控制每個工具呼叫是否執行; 不用任何東西取代提示, 只有明確 ask 規則與刪除根目錄/家目錄仍會提示

Configure the sandbox for your organization

管理員可要求所有使用者都啟用沙盒, 防止開發者放寬政策, 並讓沙盒流量走企業 proxy。

Enforce sandboxing with managed settings

{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false
  }
}
failIfUnavailable
缺少相依套件 (如 Linux 上的 bubblewrap) 時, 直接阻止 Claude Code 啟動而非退回非沙盒執行
allowUnsandboxedCommands: false
忽略 dangerouslyDisableSandbox 逃生機制, 沙盒失敗的指令無法退回非沙盒重試

Keep developers from widening the policy

布林鍵 (如 enabled) 一律採用 managed 值, 忽略開發者本機設定; 陣列鍵 (如 excludedCommands) 則會合併各層級項目。設定 allowManagedReadPathsOnly 可鎖定只採用 managed settings 的 allowRead 項目。

Custom proxy configuration

{
  "sandbox": {
    "network": {
      "httpProxyPort": 8080,
      "socksProxyPort": 8081
    }
  }
}

Troubleshooting

host-not-allowed 錯誤提示時授權, 該主機會加入允許清單供未來使用
jest 卡住或失敗watchman 與沙盒不相容, 改用 jest --no-watchman
Go CLI TLS 驗證失敗 (macOS)gh, gcloud, terraform 等工具加入 excludedCommands, 或搭配 MITM proxy 時設定 enableWeakerNetworkIsolation
open / osascript 失敗 (-600)沙盒預設封鎖 Apple Events, 需設定 allowAppleEvents 為 true (會移除程式碼執行隔離)
docker 指令失敗docker 與沙盒不相容, 將 docker * 加入 excludedCommands
容器內 bubblewrap 無法啟動非特權容器需設定 enableWeakerNestedSandbox
--dangerously-skip-permissions 以 root 執行失敗Linux/macOS 上以 root 或 sudo 執行時會被封鎖, 在辨識出的沙盒內會自動略過此檢查

Limitations 限制

選擇分類:
安全性限制
平台與工具相容性
範圍
網路過濾內建 proxy 不終止或檢查 TLS, 因此無法檢視加密連線內容, 允許過寬的網域 (如 github.com) 可能形成資料外洩管道
Unix socket 提權allowUnixSockets 可能意外授予存取強大系統服務的能力, 例如 docker.sock 等同取得主機存取權
檔案系統權限提升允許寫入 $PATH 中的目錄, 系統設定目錄或 shell 設定檔 (.bashrc 等) 可能導致跨安全情境的程式碼執行
平台支援支援 macOS, Linux, WSL2; 不支援 WSL1 與原生 Windows
效能開銷極小, 部分檔案系統操作可能稍慢
工具相容性部分需要特殊系統存取模式的工具可能需要調整設定, 或需在沙盒外執行
內建檔案工具Read, Edit, Write 直接使用權限系統, 不透過沙盒
Computer useClaude 開啟應用程式與控制螢幕時運行在實際桌面上, 而非隔離環境, 改由逐應用程式的權限提示把關
Subagents與父 session 使用相同的沙盒設定, 沙盒啟用時 subagent 內的 Bash 指令也會被沙盒化

有效的沙盒需要同時具備檔案系統與網路隔離。放寬其中一側的限制時, 請確認沒有連帶抵銷另一側的保護。
