Claude apps gateway 支出上限

依日, 週, 月為每位開發者設定支出上限, 用 Admin API 設定, Gateway 在每個請求上即時強制執行

設定上限

在 gateway.yaml 設定好 admin 區塊後, Gateway 會在 /v1/organizations/spend_limits 提供 admin API, 並在每個推論請求上即時強制執行上限。上限本身透過這個 API 設定, 不寫在 gateway.yaml 裡; 每個 POST 請求會依 scope 與 period 建立或取代一筆上限。

# 設定組織預設: 每位開發者每月 500 美元
curl -sS https://claude-gateway.internal.example.com/v1/organizations/spend_limits \
  -H "x-api-key: $GATEWAY_ADMIN_WRITE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"scope": {"type": "organization"}, "amount": "50000", "period": "monthly"}'
# contractors 群組疊加更嚴格的每日 100 美元上限
curl -sS https://claude-gateway.internal.example.com/v1/organizations/spend_limits \
  -H "x-api-key: $GATEWAY_ADMIN_WRITE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"scope": {"type": "rbac_group", "rbac_group_id": "contractors"}, "amount": "10000", "period": "daily"}'
scope.type
user, rbac_group, organization 三選一; user 用 OIDC sub 指定單一開發者, rbac_group 用 IdP 群組名稱, organization 是組織預設
amount
USD 分為單位的整數字串, 或 null 代表無上限; "0" 則會擋下每個請求
period
daily, weekly, monthly 三選一, 一個 scope 每個 period 各能持有一筆上限, 各自獨立強制執行

群組或組織上限是每個成員繼承的預設值, 不是共用額度池。每個週期內, 開發者的有效上限依序解析: 先看個人專屬覆寫, 再看最嚴格的群組上限, 再看組織預設, 最後才是無上限。

向 Admin API 認證

方式
x-api-key 標頭
Gateway bearer token
來源
符合 admin.write_keys 的金鑰享有完整存取, admin.read_keys 只能 GET
稽核紀錄
每把金鑰帶有 id, 會以 admin-key:<id> 形式出現在稽核紀錄中, 建議 Terraform, CI 與每個自動化流程各自持有專屬金鑰
來源
groups claim 包含 admin.admin_groups 其中之一的 Gateway bearer token
稽核紀錄
屬於完整存取, 以 oidc:<sub> 形式記錄, 建議人類管理員優先使用這種方式

強制執行的運作方式

1. 收到 /v1/messages 請求Gateway 用一次 Postgres 查詢解析開發者的上限與週期至今的支出
2. 超過任一上限回傳 429, error.type 為 billing_error, 標頭 x-should-retry: false, 訊息為 spend limit reached
3. 回應完成後用量計量器從串流讀取 token 數, 以 USD 牌價計費, 累加進三個週期的 Postgres 計數器
count_tokens 例外/v1/messages/count_tokens 不受限制, 因為計算 token 數本身免費
注意

支出上限是以 token 數用 USD 牌價估算, 屬於斷路器而非帳單本身。正式計費請對照供應商自己的用量報表, 例如 Anthropic Usage & Cost Admin API, Bedrock 的 invocation logs, 或 Google Cloud 的 Cloud Monitoring。未能辨識的模型 ID 會以每百萬 token 5/25 美元的預設層級計價, 而非以零計價, 避免透過未知模型繞過上限。

中斷連線也會計費

上游只在串流的最終影格回報輸出 token 數, 中斷的串流沒有這個影格。計量器會用約每四個字元一個 token 的保守下限估計值計費, 只在缺少最終用量影格時才套用, 避免開發者靠每次提早中斷來規避計費。

Postgres 可用性

Fail-open (預設)

Postgres 逾時兩秒內無法連線時, 請求會直接放行並記錄警告, 讓儲存層故障不會變成推論服務中斷。

Fail-closed

設定 enforcement.fail_closed_on_error: true 後改為拒絕, 回傳同樣的 429 billing_error, 訊息為 spend limit unavailable, 保證不會有未計量的支出。

Admin API 參考

以下端點都服務於 /v1/organizations/spend_limits 之下。

GET /spend_limits
列出已設定的上限, 支援 limit, after_id, before_id 查詢參數
POST /spend_limits
為 scope 與 period 建立或取代一筆上限
GET /spend_limits/{id}
用 spl_ 開頭的 ID 取得單一上限
DELETE /spend_limits/{id}
刪除一筆上限, 回傳 spend_limit_deleted
GET /spend_limits/effective
每個 principal 每個 period 已解析的上限與至今支出
GET /spend_limits/audit
管理員異動紀錄, 由新到舊排序

/effective

回傳 Anthropic SpendSummary 結構, 每一列是一個 principal 在某個 period 的已解析上限, 至今支出與 actor 物件。Gateway 會額外附上 groups 陣列, 記錄該 principal 最後一次已知的 IdP 群組。

user_ids[]
可重複, 依 OIDC sub 篩選特定 principal
period[]
可重複, 篩選 daily, weekly 或 monthly
sort
spend_desc 依支出高低排序, 需搭配剛好一個 period[]
q
對 OIDC sub, 最後已知 email 與顯示名稱做不分大小寫的子字串篩選
警告

q= 與 user_ids[]= 會出現在 GET 查詢字串中, 任何前端 Proxy 或負載平衡器都可能記錄進 access log, PII 政策嚴格者應在該處過濾。

資料生命週期

Gateway 持有四張與支出相關的資料表, 每小時執行一次清理以套用保留期限。

spend
每個 principal 週期至今的計數, 預設保留 13 個月
spend_limits
已設定的上限, 直到透過 API 刪除為止
admin_audit
異動紀錄, 預設保留 365 天
principal_emails
每個 principal 最後已知的 email, 顯示名稱與 IdP 群組, 含 PII, 自最後活動起預設保留 90 天
說明

identity_retention_days 刻意比 spend_retention_months 短: 停用的身分會停止更新並自然到期淘汰, 而匿名的支出計數會保留供年度比較報表使用。開發者離職時, 刪除其個人上限即可; 如需立即抹除單一使用者資料, 可直接對 Gateway 資料庫執行 DELETE FROM principal_emails WHERE principal = '<sub>'。
