把 Session 持久化到外部儲存

把 session transcript 鏡射到 S3, Redis 或自訂後端, 讓任何主機都能 resume 同一個 session。

SessionStore 介面

SessionStore 是一個物件, 有兩個必要方法 append 與 load, 以及三個選用方法。SDK 在 query 期間呼叫 append 寫入 transcript 條目, 在 resume 時呼叫 load 讀回。

append (必要)
每批 transcript 條目寫入本地後呼叫, 條目是可 JSON 序列化的物件。
load (必要)
在子行程啟動前, 當設定了 resume 時呼叫一次, 若 session 不存在則回傳 null。
listSessions (選用)
由 listSessions() 與帶 continue: true 的 query() 呼叫, 若未實作則這些呼叫會拋出例外。
delete (選用)
由 deleteSession() 呼叫, 刪除主鍵時必須連帶清除該 session 的所有子鍵, 未實作則刪除為no-op。
listSubkeys (選用)
resume 時用來找出 subagent transcript, 未實作則只會還原主 transcript。
type SessionKey = {
  projectKey: string;
  sessionId: string;
  subpath?: string; // subagent 或 sidecar 檔案時才會設定
};

快速開始

SDK 內建 InMemorySessionStore 供開發與測試使用。第一次 query 附上 store 並擷取 session ID, 第二次 query 帶著同一個 store 實例與 resume, SDK 就會改從 store 載入 transcript, 而非本地檔案系統。

const store = new InMemorySessionStore();

let sessionId;
for await (const message of query({
  prompt: "List the TypeScript files under src/",
  options: { sessionStore: store }
})) { if (message.type === "result") sessionId = message.session_id; }

// 改從 store resume, agent 擁有第一次呼叫的完整 context
query({
  prompt: "Summarize what those files do",
  options: { sessionStore: store, resume: sessionId }
});

撰寫自訂 Adapter

針對自己的後端實作 append 與 load 即可, 想讓 listSessions(), deleteSession() 與 subagent resume 生效, 再加上 listSubkeys, delete。傳入 append 的條目應視為不透明的 JSON 值, 依原順序保存, load 回傳時也必須依原順序且深度相等, 不要求位元組完全相同, 因此 Postgres jsonb 這類會重排欄位順序的後端也適用。

參考實作

TypeScript SDK repository 內附可直接執行的 S3, Redis, Postgres 參考 adapter, 未發布到 npm, 需要自行複製對應原始碼並安裝後端 client。

S3SessionStore
用 @aws-sdk/client-s3, 每次 append() 產生一個 JSONL part file, load() 時列出, 排序後串接。
RedisSessionStore
用 ioredis, 每份 transcript 對應一個 RPUSH/LRANGE list, 另有排序集合作為 session 索引。
PostgresSessionStore
用 pg, 每個條目在 jsonb 資料表中各佔一列, 依 BIGSERIAL 排序。
驗證

兩個 SDK 都附有一致性測試套件, 用來驗證 append, load 與選用方法是否符合行為約定; 未實作的選用方法測試會自動跳過。Python 可直接從套件呼叫 run_session_store_conformance(MyRedisStore)。

保留政策

store 是鏡射而非取代, Claude Code 子行程一律先寫入本地磁碟, SDK 再把每批資料轉送給 append()。sessionStore 不能與 persistSession: false 或 enableFileCheckpointing 同時使用, 設定兩者會直接拋出例外。

append() 失敗時 SDK 最多再重試兩次, 合計三次嘗試, 逾時的呼叫不會重試。仍失敗則記錄錯誤, 送出 mirror_error 系統訊息並捨棄該批次繼續執行, 本地 transcript 已經落地不受影響。因為重試批次可能重送已寫入的條目, 實作 append() 時應以 entry.uuid 去重。

getSessionMessages({ sessionStore }) 回傳的是 resume 時 agent 會看到的鏈結訊息, 也就是自動壓縮後的版本, 一個 store 裡有 503 筆原始條目的 session 可能只回傳 18 則訊息。要取得完整原始歷史需直接呼叫 store.load(key)。

forkSession({ sessionStore }) 不是位元組複製, 而是讀出來源條目, 重寫每一筆 sessionId 欄位並重新映射訊息 UUID, 再以新的 key 寫入, 因此無法用 adapter 層級的複製或 CopyObject 捷徑完成, 那樣會產生仍引用舊 session ID 的 transcript。

subagent transcript 會鏡射在 subpath: "subagents/agent-<id>" 底下。listSubagents 需要 adapter 實作 listSubkeys, getSubagentMessages 若沒有該方法則退回直接讀取 subpath, resume 時也會呼叫 listSubkeys 還原 subagent 檔案。

SDK 不會主動從你的 store 刪除資料, 保留策略是 adapter 自己的責任, 可用 TTL, S3 lifecycle policy 或排程清理來符合合規需求。本地 transcript 則由 CLAUDE_CONFIG_DIR 下的 cleanupPeriodDays 設定獨立清掃。

支援 sessionStore 選項的函式

query()建立並執行對話
startup()啟動階段設定
listSessions()列舉所有 session
getSessionInfo() / getSessionMessages()讀取單一 session 資訊與訊息
renameSession() / tagSession()重新命名或標記 session
deleteSession() / forkSession()刪除或分岔 session
listSubagents() / getSubagentMessages()讀取 subagent transcript
