追蹤成本與用量

了解如何追蹤 token 用量, 估算成本, 並設定 Agent SDK 的 prompt caching

警告

total_cost_usd 與 costUSD 欄位是客戶端估算值, 並非權威帳單資料。SDK 是根據建置時內建的價格表在本地計算, 可能因定價變動, SDK 版本不認得新模型, 或無法建模的計費規則而產生落差。請以 Usage and Cost API 或 Console 的 Usage 頁面作為權威依據。

了解 token 用量

Cost tracking 的關鍵是理解 SDK 如何劃分用量資料的範圍。

query() call
一次 query() 呼叫, 可包含多個步驟, 結束時產生一則 result 訊息
Step
query() 呼叫內的一次請求/回應循環, 每步驟都會產生帶有 token 用量的 assistant 訊息
Session
透過 resume 選項串連的一系列 query() 呼叫, 每次呼叫各自回報自己的成本

訊息串流的兩個步驟

1 · 每步驟產生 assistant 訊息
2 · result 訊息提供累計估算

Claude 回應時會送出一或多則 assistant 訊息。當 Claude 在同一輪呼叫多個工具時, 該輪所有訊息共用相同 ID, 需依 ID 去除重複以避免重複計算。

query() 呼叫完成時, SDK 會發出帶有 total_cost_usd 與累計 usage 的 result 訊息。若你只需要估算總額, 可以忽略每步驟用量, 只讀這個值即可。

取得 query 的總成本

result 訊息標誌著 query() 呼叫的 agent loop 結束, 內含 total_cost_usd, 也就是該次呼叫所有步驟的累計估算成本。

for await (const message of query({ prompt: "Summarize this project" })) {
  if (message.type === "result") {
    console.log(`Total cost: $${message.total_cost_usd}`);
  }
}

追蹤每步驟與每個模型的用量

切換視角: 每步驟用量 每模型用量

每則 assistant 訊息內含一個 id 與 usage 物件。平行工具呼叫會產生多則共用相同 id 與相同用量資料的訊息, 務必依 ID 去除重複以取得正確的每步驟 token 計數。

const seenIds = new Set();
let totalInputTokens = 0;

for await (const message of query({ prompt })) {
  if (message.type === "assistant") {
    const msgId = message.message.id;
    if (!seenIds.has(msgId)) {
      seenIds.add(msgId);
      totalInputTokens += message.message.usage.input_tokens;
    }
  }
}

result 訊息包含 modelUsage, 一個模型名稱對應每個模型 token 計數與成本的表, 適合觀察多模型 (例如 Haiku 處理 subagent, Opus 處理主 agent) 的用量分佈。

for (const [modelName, usage] of Object.entries(message.modelUsage)) {
  console.log(`${modelName}: $${usage.costUSD}`);
}

累計多次呼叫的成本

每次 query() 呼叫回傳自己的 total_cost_usd。SDK 不提供 session 層級的總額, 若應用程式進行多次呼叫, 需要自行累加。

在多輪 session 或跨使用者的情境下, 於每次 result 訊息抵達時把 total_cost_usd 加進自己維護的累計變數, 才能得到完整的花費總覽。

處理錯誤, 快取與 token 落差

1 · 輸出 token 落差
2 · 失敗對話的成本
3 · 快取 token
4 · 延長快取 TTL

同一 ID 的訊息偶爾會出現不同的 output_tokens 值。此時應採用較高的數值, 並優先信任 result 訊息中的 total_cost_usd, 它比自行加總每步驟數值更可靠。

成功與錯誤的 result 訊息都包含 usage 與 total_cost_usd。對話中途失敗時, 已耗用的 token 仍需計入, 務必無論 subtype 為何都讀取成本資料。

usage 物件包含 cache_creation_input_tokens (建立新快取項目, 費率較高) 與 cache_read_input_tokens (讀取既有快取, 費率較低), 應與 input_tokens 分開追蹤以了解快取節省效果。

使用 API key 或跑在 Bedrock, Vertex, Foundry 上時, 快取寫入預設 TTL 為 5 分鐘。設定 ENABLE_PROMPT_CACHING_1H 環境變數可要求 1 小時 TTL, 適合間隔超過 5 分鐘的短 session 工作負載, 但 1 小時 TTL 的寫入費率較高。
