Agent SDK Sessions

了解 session 如何保存 agent 對話歷史, 以及何時該用 continue, resume 或 fork 回到先前的執行紀錄。

選擇合適的做法

需要多少 session 管理, 取決於應用程式的形狀。單一 query() 呼叫內, agent 本來就會自行完成所需的多輪對話, 只有當你要發送多個彼此需共享上下文的 prompt 時, session 管理才會派上用場。

單次任務
單一 prompt, 無需後續追問, 一次 query() 呼叫即可處理。
單一行程內多輪對話
Python 用 ClaudeSDKClient, TypeScript 用 continue: true, SDK 自動追蹤 session, 不需處理 ID。
行程重啟後接續
continue_conversation=True / continue: true, 自動接續目錄中最近一次 session, 不需 ID。
回到特定過去 session
擷取 session ID 並傳入 resume。
嘗試替代方案但保留原始紀錄
使用 fork 分岔 session。
無狀態任務 (僅 TypeScript)
設定 persistSession: false, session 只存在記憶體中, Python 則一律會寫入磁碟。

Continue, Resume 與 Fork

三者都是設定在 query() 上的選項欄位, 差別在於如何找到與處理既有的 session。

選擇概念:
Continue
Resume
Fork

尋找目前目錄中最近一次的 session 並接續下去, 不需要自行追蹤任何 ID, 適合一次只跑一組對話的應用程式。

傳入特定的 session ID 來接續, 你需要自行追蹤這個 ID。當有多組 session 並存 (例如多使用者各自一組), 或想回到非最近一次的 session 時使用。

建立一份全新的 session, 內容是原始歷史的副本, 原始 session 完全不受影響。適合想嘗試不同方向, 同時保留退回原路的選項。

自動 Session 管理

兩個 SDK 都提供跨呼叫自動追蹤 session 狀態的介面, 不需要手動傳遞 ID, 適合單一行程內的多輪對話。

Python: ClaudeSDKClient

內部自動處理 session ID, 每次呼叫 client.query() 都會自動接續同一個 session。

async with ClaudeSDKClient(options=options) as client:
    await client.query("Analyze the auth module")
    async for message in client.receive_response():
        print_response(message)
    await client.query("Now refactor it to use JWT")
TypeScript: continue: true

沒有像 ClaudeSDKClient 那樣的物件, 改為在每次後續呼叫傳入 continue: true, SDK 會找到目前目錄中最近一次的 session。

for await (const message of query({
  prompt: "Now refactor it to use JWT",
  options: { continue: true }
})) { /* ... */ }
注意

實驗性的 V2 session API (createSession 搭配 send / stream) 已在 TypeScript Agent SDK 0.3.142 中移除, 請改用 query() 函式與本頁介紹的 session 選項。

用 query() 操作 Session 選項

1 · 擷取 Session ID
2 · 依 ID Resume
3 · Fork 探索替代方案

resume 與 fork 都需要 session ID。從結果訊息的 session_id 欄位讀取即可, 每一則結果訊息都會帶有這個欄位, 無論成功或錯誤。TypeScript 在 init 的 SystemMessage 上也能更早取得; Python 則巢狀在 SystemMessage.data 內。

let sessionId;
for await (const message of query({ prompt: "Analyze the auth module" })) {
  if (message.type === "result") sessionId = message.session_id;
}

把 session ID 傳給 resume 即可回到該 session, agent 會帶著完整先前上下文接續下去。常見情境: 針對已完成的分析追加後續動作, 從 error_max_turns 之類的上限中恢復, 或是行程重啟後還原對話。

query({
  prompt: "Now implement the refactoring you suggested",
  options: { resume: sessionId }
});
常見錯誤

若 resume 回傳的是全新 session 而非預期歷史, 最常見原因是 cwd 不一致。session 儲存在 ~/.claude/projects/<encoded-cwd>/*.jsonl, 若從不同目錄呼叫 resume, SDK 會找錯位置。

fork 會建立一份帶有原始歷史副本的新 session, 但從那個時間點開始分岔發展。fork 會取得自己的 session ID, 原始 session 的 ID 與歷史則完全不變, 你會得到兩個可各自獨立 resume 的 session。

query({
  prompt: "Instead of JWT, outline how OAuth2 would work",
  options: { resume: sessionId, forkSession: true }
});
注意

fork 只分岔對話歷史, 不分岔檔案系統。若 forked agent 編輯了檔案, 那些變更是真實且對同目錄下其他 session 可見的, 要分岔並還原檔案變更請用 file checkpointing。

Step 1 of 3

跨主機 Resume

session 檔案只存在於建立它的機器上。要在不同主機 (CI worker, 短暫容器, serverless) resume, 有兩種做法。

搬移 session 檔案

把 ~/.claude/projects/<encoded-cwd>/<session-id>.jsonl 從第一台機器複製到新主機的相同路徑, cwd 必須一致。

不依賴 session resume

把需要的結果 (分析輸出, 決策, 檔案差異) 存成應用程式狀態, 再傳入新 session 的 prompt, 通常比搬運 transcript 檔案更穩健。

兩個 SDK 都提供 listSessions() / getSessionMessages() 等函式可列舉與讀取磁碟上的 session, 也提供 getSessionInfo(), renameSession(), tagSession() 等函式用來管理個別 session。
