Create plugins

Create custom plugins to extend Claude Code with skills, agents, hooks, and MCP servers.

When to use plugins vs standalone configuration

Standalone (.claude/)

Skill names like /hello. Best for personal workflows, project-specific customizations, quick experiments.

Plugins

Skill names like /plugin-name:hello. Best for sharing with teammates, distributing to a community, versioned releases, reuse across projects.

Start with standalone configuration in .claude/ for quick iteration, then convert to a plugin when ready to share.

Every plugin lives in its own directory. Location doesn't matter for this quickstart since --plugin-dir points at it directly.

mkdir my-first-plugin/.claude-plugin
// my-first-plugin/.claude-plugin/plugin.json
{
  "name": "my-first-plugin",
  "description": "A greeting plugin to learn the basics",
  "version": "1.0.0",
  "author": { "name": "Your Name" }
}
name
Unique identifier and skill namespace, e.g. /my-first-plugin:hello
description
Shown in the plugin manager
version
Optional; omit to use commit SHA versioning
author
Optional attribution
mkdir -p my-first-plugin/skills/hello
---
description: Greet the user with a friendly message
disable-model-invocation: true
---

Greet the user warmly and ask how you can help them today.
claude --plugin-dir ./my-first-plugin
/my-first-plugin:hello
WHY NAMESPACING?

Plugin skills are always namespaced (like /my-first-plugin:hello) to prevent conflicts between plugins. Change the prefix by editing plugin.json's name field.

---
description: Greet the user with a personalized message
---

# Hello Skill

Greet the user named "$ARGUMENTS" warmly and ask how you can help them today.
/reload-plugins
/my-first-plugin:hello Alex
Step 1 of 5

Develop a plugin in your skills directory

Instead of passing --plugin-dir every launch, keep a plugin in the skills directory:

claude plugin init my-tool

Creates ~/.claude/skills/my-tool/ with a manifest and starter SKILL.md. Loads next session as my-tool@skills-dir with no marketplace or install step.

Plugin structure overview

COMMON MISTAKE

Don't put commands/, agents/, skills/, or hooks/ inside .claude-plugin/. Only plugin.json goes there. All other directories must be at the plugin root — which is the individual plugin's own directory, never ~/.claude/.

.claude-plugin/
Contains plugin.json manifest (optional)
skills/
<name>/SKILL.md directories
commands/
Skills as flat markdown files (legacy; use skills/)
agents/
Custom agent definitions
hooks/
Event handlers in hooks.json
.mcp.json / .lsp.json
MCP / LSP server configurations
monitors/
Background monitor configurations
bin/
Executables added to the Bash tool's PATH
settings.json
Default settings applied when enabled

A plugin with exactly one skill can place SKILL.md directly at the plugin root instead of creating a skills/ directory.

Skills are model-invoked — Claude uses them automatically based on task context. Run /reload-plugins after installing.

// .lsp.json
{ "go": { "command": "gopls", "args": ["serve"], "extensionToLanguage": { ".go": "go" } } }

For common languages, install pre-built LSP plugins from the official marketplace instead. Users installing a custom LSP plugin must have the language server binary installed themselves.

// monitors/monitors.json
[
  { "name": "error-log", "command": "tail -F ./logs/error.log", "description": "Application error log" }
]

Claude Code starts each monitor automatically when the plugin is active; each stdout line is delivered to Claude as a notification.

// settings.json
{ "agent": "security-reviewer" }

Only agent and subagentStatusLine keys are supported. Setting agent activates a plugin agent as the main thread — its prompt, tool restrictions, and model. Takes priority over settings in plugin.json; unknown keys are ignored.

claude --plugin-dir ./my-plugin
claude --plugin-dir ./my-plugin.zip  # v2.1.128+
claude --plugin-dir ./plugin-one --plugin-dir ./plugin-two

A --plugin-dir plugin with the same name as an installed marketplace plugin takes precedence for that session (except force-enabled/disabled managed plugins). Run /reload-plugins after edits. Test with /plugin-name:skill-name, check /context for agents, verify hooks.

claude --plugin-url https://example.com/my-plugin.zip --plugin-url https://example.com/other.zip

Fetches and loads a hosted .zip archive for that session only; only point this at archives you trust.

  1. Check the structure: directories at plugin root, not inside .claude-plugin/
  2. Test components individually: skills, agents, hooks separately
  3. Use validation/debugging tools per the Plugins reference

Share your plugins

  1. Add documentation: a README.md with install and usage instructions
  2. Choose a versioning strategy: explicit version or git commit SHA
  3. Create or use a marketplace to distribute
  4. Test with team members before wider distribution

Submit your plugin to the community marketplace

claude-plugins-official

Curated by Anthropic, registered automatically on first interactive launch. No application process for inclusion.

claude-community

Public marketplace where third-party submissions land after review. Add with /plugin marketplace add anthropics/claude-plugins-community.

Submit via claude.ai's directory submissions form (Team/Enterprise) or the Console form (individual authors). Run claude plugin validate before submitting — the review pipeline runs the same check plus automated safety screening. Approved plugins are pinned to a commit SHA in the community catalog and synced nightly.

mkdir -p my-plugin/.claude-plugin
{ "name": "my-plugin", "description": "Migrated from standalone configuration", "version": "1.0.0" }
cp -r .claude/commands my-plugin/
cp -r .claude/agents my-plugin/
cp -r .claude/skills my-plugin/
mkdir my-plugin/hooks
{
  "hooks": { "PostToolUse": [{ "matcher": "Write|Edit",
    "hooks": [{ "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npm run lint:fix" }] }] }
}
claude --plugin-dir ./my-plugin

Test each component: run commands, check agents in /context, verify hooks trigger.

What changes when migrating

Only in one project→ Can be shared via marketplaces
.claude/commands/→ plugin-name/commands/
Hooks in settings.json→ hooks/hooks.json
Manually copy to share→ Install with /plugin install
NOTE

After migrating, remove the original .claude/ files to avoid duplicates. Project/user .claude/agents/ definitions override same-named plugin agents.
